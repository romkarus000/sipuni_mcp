# Sipuni MCP: рабочие правила

## Назначение

Этот репозиторий содержит TypeScript MCP-сервер для аналитики телефонии Sipuni и сверки со CRM.
Целевой результат работы:

- дать авторизованным пользователям безопасный доступ к MCP-инструментам;
- возвращать короткую, понятную и проверяемую статистику по звонкам;
- связывать звонки с последующими оплатами и статусами клиентов в CRM;
- обеспечивать быстрые ответы за счёт пакетных запросов, индексов, кэша и предрасчётов.

## Текущее устройство

- `src/index.ts` — MCP stdio-транспорт, объявления и обработчики инструментов.
- `src/sipuni.ts` — подписанный запрос к `Sipuni /api/statistic/export`, CSV-парсинг и нормализация звонков.
- `src/db.ts` — пул MySQL и запросы к `sales_manager`, `user_detail`, `timeline`.
- Переменные `SIPUNI_USER` и `SIPUNI_SECRET` обязательны. CRM подключается только при полном наборе `DB_HOST`, `DB_USER`, `DB_NAME` (а также обычно `DB_PASSWORD`, `DB_PORT`).

Текущие инструменты возвращают сырые вызовы, KPI одного менеджера и непривязанные звонки. Они ещё не дают статистику оплат и CRM-статусов.

## Команды

```bash
npm ci
npm run build
npm start
```

До изменений, затрагивающих расчёты, добавляйте или обновляйте тесты. Минимальная проверка перед передачей работы: `npm run build`.

## Правила разработки

### Контракты MCP и ответы

- Не меняйте имена, входные поля или смысл существующих инструментов без обратно совместимого перехода.
- Валидируйте формат дат, границы периода, часовой пояс и лимиты результата до обращения к Sipuni или CRM.
- Ответ должен начинаться с компактного `summary`, затем содержать период, часовой пояс, применённые фильтры, источник/время обновления и только нужные детали.
- Не отдавайте весь массив звонков по умолчанию. Для детализации используйте `include_details`, пагинацию/лимит и стабильную сортировку.
- Числа передавайте как числа, длительности — в секундах и дополнительно в удобном формате, проценты — с явно указанным знаменателем.
- Для пустых данных возвращайте валидный нулевой отчёт, а не ошибку. Для ошибок API/БД возвращайте безопасное диагностическое сообщение без секретов.

### Производительность и данные

- Запрашивайте Sipuni один раз на период и используйте результат для всех агрегатов этого запроса.
- Для CRM всегда используйте один пакетный запрос по набору ID/телефонов/диапазону дат, а не запрос внутри цикла. Допустимы `JOIN`, CTE, временная таблица или пакетные `IN` с разумным разбиением.
- Агрегируйте в SQL, если данные уже находятся в CRM; не переносите большие наборы в Node.js ради подсчётов.
- Перед новыми тяжёлыми запросами проверяйте `EXPLAIN` и добавляйте миграцию индекса вместе с запросом. Не применяйте миграции в production без явного согласования.
- Вводите ограниченный TTL-кэш для неизменяемых/почти неизменяемых периодов и инкрементальное обновление для текущего дня. Ключ кэша обязан включать аккаунт, период, часовой пояс и фильтры.
- Оплаты связывайте по явно документированному правилу: нормализованный телефон/CRM-сущность, окно атрибуции после звонка, приоритет менеджера и защита от двойного учёта. В отчёте показывайте это правило и число несопоставленных записей.
- Не выполняйте N+1: список менеджеров, звонков, статусов и оплат должен загружаться батчами.

### Корректность аналитики

- Все даты хранятся и фильтруются с явно заданным часовым поясом. Отдельно тестируйте границы суток и переходы месяца.
- Разделяйте: попытки, уникальные звонки, отвеченные, пропущенные, длительность звонка и длительность разговора. Не включайте внутренние звонки в клиентские KPI без явного флага.
- Документируйте маппинг статусов Sipuni и CRM, а неизвестные значения сохраняйте как `unknown` с количеством в отчёте.
- Учитывайте дубликаты и повторные выгрузки через стабильный идентификатор звонка (`callId`/`recordId`).

### Безопасность и доступ пользователей

- Никогда не добавляйте `.env`, ключи Sipuni, пароли БД, дампы БД или телефонные номера клиентов в Git, логи и тестовые фикстуры.
- Stdio MCP не является пользовательским публичным API. Для внешнего доступа проектируйте отдельный аутентифицированный шлюз/совместимый MCP-транспорт с TLS, разграничением ролей, аудитом, rate limit и ограничением доступных периодов/данных.
- Доступ к CRM предоставляйте read-only пользователю и предпочтительно к реплике. Не запускайте аналитические запросы на primary-БД.
- Маскируйте номера телефонов и персональные данные по умолчанию; полные детали выдавайте только роли с явным разрешением.
- Секреты передавайте через менеджер секретов или защищённые переменные окружения, не через аргументы командной строки.

## Сервер и развёртывание

- На сервере `46.149.70.15` на момент анализа установлен Node.js `v12.22.9`, тогда как проект требует Node.js 18+. Перед развёртыванием установить поддерживаемый LTS (предпочтительно Node 20+) и запускать сервис отдельным непривилегированным пользователем.
- На сервере уже работают Docker, Nginx, n8n и Metabase. Не меняйте их конфигурацию и не публикуйте новый порт без отдельного плана развёртывания и согласования.
- Добавляйте health-check, структурированные логи без PII, рестарт-политику и метрики: время ответа Sipuni/CRM, cache hit rate, размер батча, ошибки и число обработанных звонков.

## Перед изменением схемы CRM

Сначала получите и зафиксируйте фактические таблицы и связи для клиентов, сделок/заказов, оплат и статусов. Не угадывайте названия таблиц или семантику статусов. После этого опишите в коде и документации правило атрибуции «звонок → клиент → оплата/статус» и покройте его тестовыми сценариями.
